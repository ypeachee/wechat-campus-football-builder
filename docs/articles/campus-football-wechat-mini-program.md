# 我用 AI 做了一个校园足球小程序：真正难的不是写代码

> 副标题：从赛事模型、权限设计到微信审核，一次完整的产品工程复盘

过去一段时间，我用 AI 协作完成了一套“CUGB 校园足球”微信小程序：可以看球队、球员、赛程、积分榜、射手榜和助攻榜；可以维护多位管理员和球队管理员；支持联赛、杯赛、小组积分和淘汰赛树；比赛结束后还能给球员和主裁打分。

表面上看，这是一次“让 AI 帮我写代码”的实验。做完之后，我最大的感受却是：

**AI 确实大幅降低了写代码的成本，但它不会替你决定产品应该怎么建模。**

代码写错可以改，模型设计错、权限边界错、数据口径错，后面会不断返工。真正值得复盘的，不是某个页面怎么写，而是那些看起来不性感、却决定项目能不能长期维护的约束。

---

## 一、先定数据模型，否则 AI 只会更快地做出错误产品

一个足球赛事系统，最容易被低估的是“比赛数据”到底由哪些东西组成。

一开始很容易把所有信息都塞进一张比赛表：比分、进球、助攻、红黄牌、谁首发、谁替补……但这样很快会出现一个问题：同一件事有多个来源，统计口径开始互相打架。

最后我把核心数据拆成了几层。

### 1. 赛事层级

```text
competition 赛事
└── season 赛季
    └── stage 阶段
        ├── group 小组
        └── knockout 淘汰赛
```

这样同一个系统里可以同时存在：

- 校园联赛：一个赛季一个联赛阶段，一张总积分榜。
- 校园杯赛：小组赛阶段 + 淘汰赛阶段。
- 未来其他赛事：不需要再复制一套比赛表。

赛事类型只是管理端推荐的流程，真正的结构由阶段决定。阶段可以是 `LEAGUE`、`GROUP` 或 `KNOCKOUT`。

### 2. 积分榜不单独建表

积分榜是最典型的高风险冗余数据。

如果每录入一场比赛，就同时更新一张积分榜表，那么只要某次更新失败、比分被修改、比赛被取消，积分榜就可能和比赛结果不一致。

所以我的选择是：**积分榜从已完赛比赛动态计算。**

场次、胜平负、进球、失球、净胜球和积分都由比赛结果聚合得到。这样会多一次查询，但少了一个长期维护的“第二真相”。

只有在性能真的成为问题时，才值得增加缓存；而且缓存必须有明确的失效规则。

### 3. 比赛事件和出场记录必须分开

这是另一个很容易被混淆的地方。

`fixture_event` 回答的是“比赛中发生了什么”：进球、助攻、黄牌、红牌。

`fixture_appearance` 回答的是“谁参加了比赛”：首发还是替补、踢了多少分钟。

这两类数据不能合并。一个球员可以出场但没有进球；一个进球事件也必须能关联到具体的比赛和球员。助攻可以挂在进球事件上，而不需要再创造一条完全独立的助攻记录，否则很容易出现“进球有助攻、助攻榜却没有”的不一致。

### 4. 阵容录入应该整队保存

最新一轮优化里，我把“逐条新增出场”改成了“整队勾选”。

每支球队显示完整名单：

- 首发区从球队名单中勾选。
- 替补区仍然显示完整名单。
- 已经入选首发的球员在替补区继续保持勾选，但锁定，不能重复选择。
- 每名替补可以填写出场分钟。
- 保存时，一支球队的阵容作为一个事务整体替换。

球员名称统一显示为 `10 姆巴佩`，不写成“10号姆巴佩”。看起来只是文案细节，但它会影响所有页面的识别一致性。

后端还加了几条保护：

- 同一个球员不能同时出现在首发和替补。
- 球员必须属于该球队。
- 已经有比赛事件的球员不能被无声删除。
- 重复保存同一个阵容，最终状态一致。
- 所有修改写入审计日志。

这类“批量操作”比单条 CRUD 更接近真实管理场景，也更需要事务和幂等思维。

## 二、权限不是前端隐藏按钮

这个项目的第一版权限模型很小，但已经足够覆盖真实场景：

| 角色 | 能做什么 |
|---|---|
| `ADMIN` | 管理赛事、赛程、比分、阵容、淘汰赛、评分审核 |
| `TEAM_MANAGER` | 只能维护被授权球队的资料、球员、出场和事件 |
| `VIEWER` | 浏览公开内容，只读 |

最重要的原则是：**前端入口只负责导航，权限判断必须在后端。**

一个球队管理员即使手动构造了另一个球队的请求，后端也必须拒绝。每次请求都要重新从数据库加载角色和球队授权，不能只相信 JWT 里的旧信息。

项目里还有几个权限边界：

- 球队必须是这场比赛的参赛球队。
- 球队管理员只能操作自己被授权的球队。
- 锁定比赛的所有写操作都必须被拦截，管理员也不例外。
- 淘汰赛胜者、点球比分、晋级规则和决赛树只允许管理员修改。
- 评分审核、隐藏、恢复和敏感词管理进入审计日志。

这样做会让接口实现多一点代码，但能避免“页面上看不到按钮”被误认为“系统已经安全”。

## 三、赛制不是一张积分榜，而是一棵状态树

联赛相对简单，杯赛复杂得多。

一个杯赛里，球队先从小组赛晋级，进入淘汰赛；淘汰赛需要对阵、晋级、点球、决赛和冠军。每一次上游结果变化，都可能影响下游。

因此我把杯赛拆成了几个明确概念：

- 小组积分榜只统计本小组的比赛。
- 小组名次通过明确规则映射到淘汰赛首轮位置。
- 单场淘汰赛必须产生唯一胜者。
- 常规时间打平必须有有效点球比分。
- 胜者自动进入下一轮配置的位置。
- 如果下游比赛已经有数据，就不能随意覆盖上游结果。
- 决赛胜者成为冠军。
- 所有种子、分组、对阵和晋级操作由管理员完成。

这套模型的关键不是“能画出一棵决赛树”，而是每次结果变化都知道下游是否已经依赖它。否则一个看似简单的比分修改，可能悄悄破坏整棵树。

## 四、评分功能不是加五颗星，而是引入 UGC

比赛结束后给球员打分，是很有体育产品味道的功能。

我们采用了 5 星输入、10 分制展示：

```text
1 星 -> 2 分
2 星 -> 4 分
3 星 -> 6 分
4 星 -> 8 分
5 星 -> 10 分
```

但这不只是一个评分控件。只要允许用户填写短评，产品就从“只读数据展示”变成了 UGC 服务。

因此评分系统同时需要：

- 只有比赛结束后才能评分。
- 只能评价有出场记录的球员。
- 每个用户每场每名球员只能有一条评分。
- 24 小时内允许修改一次。
- 短评经过本地敏感词和微信内容安全检查。
- 待审核、拒绝和隐藏的内容不计入公开平均分。
- 提供举报入口。
- 管理员可以审核、隐藏和恢复内容。
- 不公开用户 OpenID 等非必要信息。
- 微信内容安全服务异常时，生产环境不能直接放行。

主裁评分也复用了 5 星到 10 分的模型，但不提供文字评价，所以不触发短评审核流程。

这就是一个典型的产品工程问题：**按钮很小，合规和状态机并不小。**

## 五、AI 协作最有效的方式：垂直切片，而不是大爆炸开发

我并没有一次性告诉 AI “给我做一个完整小程序”。更有效的方式是按垂直切片推进：

```text
一个明确的用户结果
-> 数据表/迁移
-> 服务层规则
-> API
-> 小程序服务调用
-> 页面状态和交互
-> 自动化测试
-> 实际启动和 smoke test
```

例如“整队维护阵容”这个需求，验收标准包括：

- 首发可从完整名单勾选。
- 替补区保留首发并锁定。
- 保存后整队替换。
- 跨队、重复和锁定比赛被拒绝。
- 已产生事件的球员不能被删除。
- 有后端集成测试和前端请求测试。

这样做有几个好处：

1. 每次只改一条完整链路，容易定位问题。
2. AI 有明确的验收标准，不会只生成“看起来像”的页面。
3. 测试覆盖的是业务不变量，而不是表面文案。
4. 后继功能可以复用前面已经稳定下来的模型。

AI 最擅长的不是替你做所有决定，而是在你给出约束之后，快速完成重复的实现、补测试、查日志和做回归。

## 六、微信小程序上线，真正花时间的是环境

开发阶段最容易误判的一件事，是把“本地能跑”当成“可以上线”。

微信小程序至少有三套环境：

| 环境 | API 地址 | 关键点 |
|---|---|---|
| 开发者工具 | 本地 `127.0.0.1` | 可关闭域名校验 |
| 体验版 | 测试服务器 | 必须 HTTPS、合法域名 |
| 正式版 | 生产服务器 | HTTPS、稳定域名、监控和备份 |

### 登录 401 不一定是域名问题

登录失败通常要先检查：

- 小程序 AppID 和后端 AppSecret 是否匹配。
- 后端进程是否真的读到了环境变量。
- 修改环境变量后是否重启了后端。
- 微信 code 是否过期或已经被使用。
- 服务器能否正常访问微信接口。
- 数据库迁移和管理员初始化是否完成。

### AppSecret 绝对不能放到小程序里

小程序只拿临时 `code`，交给自己的后端换取登录态。`AppSecret`、JWT 密钥、数据库密码只能存在于后端环境变量或密钥管理中。

### 体验版必须使用 HTTPS 合法域名

`localhost` 和 `127.0.0.1` 只适合开发。体验版和正式版需要：

- 可公网访问的域名。
- 有效的 HTTPS 证书。
- 在微信后台配置 request 合法域名。
- 真机测试 DNS、证书链和网络。

### 开发者工具日志要分类看

日志里有一些是提示，不是错误：

- “已关闭合法域名校验”：本地开发的预期状态。
- 灰色基础库提示：通常只是调试信息。
- 资源预加载警告：没有加载失败时一般不是业务问题。
- 页面未注册、组件路径不存在、HTTP 401/403/404：这些才是真正的编译或接口问题。

尤其是“页面未注册”，应先看 `app.json`，不要因为控制台里同时出现网络错误就误判为域名问题。

## 七、最后，AI 不能替你负责产品判断

这次项目让我更确定一件事：

**AI 让“写出来”变便宜了，但让“想清楚”变重要了。**

真正决定项目质量的，仍然是这些问题：

- 积分榜从哪里来？
- 事件和出场记录是不是同一件事？
- 阵容保存失败时，旧数据是否还能保留？
- 球队管理员能不能绕过前端直接改别人的球队？
- 已完赛的比赛为什么还能被编辑？
- 评分为何会变成内容审核问题？
- 小程序体验版为什么不能直接访问本地后端？

这些问题没有一条是某个框架自动帮你解决的。

但它们可以被整理成可复用的工作流。

我已经把这次项目中的领域模型、权限边界、比赛数据规则、评分审核和微信上线清单整理成一个 GitHub Skill，后续做类似项目时，可以让 AI 直接按这些约束工作，而不是每次从零解释。

---

## 结语

这套小程序最后呈现出来的，是一组普通页面：球队、赛程、榜单、详情和管理台。

但页面背后，是一套更重要的东西：

**数据只有一个可信来源，权限只在服务端生效，赛制变化有明确状态，用户内容先审核再公开。**

如果你也在做校园赛事、社团活动或垂直体育产品，希望这篇复盘能帮你少踩一点坑。

AI 可以帮你把系统写得更快，但系统为什么可信，仍然需要你自己定义。
